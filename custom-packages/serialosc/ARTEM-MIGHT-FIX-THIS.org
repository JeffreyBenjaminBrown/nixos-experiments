** Short conclusion

PR [[https://github.com/monome/serialosc/pull/88][serialosc #88]] does not fix the bug on this machine.  Its added
=POLLNVAL= and supervisor/OSC-descriptor checks are not supported by the
evidence, and the affected Nix build does not compile =event_loop/poll.c= at
all.  (This describes the original broken build; the local repair described
below now compiles =poll.c= and has passed a physical unplug test.)

The trace identified this chain:

1. serialosc's configure probe incorrectly reports that =poll()= does not work,
   so serialosc builds =event_loop/select.c=.
2. The monome is unplugged.  Linux reports the grid tty as readable/hung up,
   but it does not put this condition in =select()='s exceptional-descriptor
   set.
3. The select event loop calls =monome_event_handle_next()=.
4. libmonome's internal one-descriptor =poll()= sees exactly =0x19=:
   =POLLIN | POLLERR | POLLHUP=.  There is no =POLLNVAL=.
5. libmonome returns an error, but serialosc's select event loop ignores the
   return value.  It immediately repeats, consuming a core.

This is remarkably close to [[https://github.com/monome/serialosc/issues/10][serialosc issue #10]] from 2013.  In that issue
Artem confirmed that the problem occurred when serialosc mistakenly built the
select event loop and disappeared when the poll event loop was used.

** Direct answers to Artem's questions

*** Which descriptor?

The monome device descriptor, fd 3 in the capture, referring to the removed
=/dev/ttyUSB0=.  It was not the liblo OSC socket and not the supervisor IPC
descriptor.

*** Which flag check is missing?

For the observed problem, none is missing from serialosc's *poll* event loop.
That loop already checks =POLLHUP | POLLERR=, and the kernel returned both.

The running binary had compiled the *select* event loop instead.  Its
exceptional-descriptor check did not signal this tty hangup.  The missing
behavior is to respect the negative return from =monome_event_handle_next()=.

*** Is POLLNVAL involved?

No.  Every captured post-unplug result had
=POLLIN | POLLERR | POLLHUP= (=0x19=) and no =POLLNVAL=.

*** When does the supervisor fd become invalid?

There is no demonstrated case in this bug.  The checks added for =fds[1]= and
=fds[2]= in PR #88 were speculation and should be removed.

*** Why did the original two patches seem to improve CPU use?

They were applied together, the service was rebuilt/restarted, and the result
was not isolated by patch or event-loop backend.  The present evidence cannot
attribute that observation to either patch.  In particular, serialosc #88
changes =poll.c= while the Nix build log proves that this system built
=select.c=.

** Recommended upstream changes

*** Fix the configure probe

#+begin_src diff
diff --git a/wscript b/wscript
--- a/wscript
+++ b/wscript
@@
 	code = """
 		#include <stdlib.h>
+		#include <fcntl.h>
 		#include <poll.h>
#+end_src

This restores the intended poll backend on Linux with modern compilers.  On
this device, the existing poll event-loop check is sufficient for the captured
=0x19= state.

*** Make the select fallback terminate on a libmonome read error

#+begin_src diff
diff --git a/src/serialosc-device/event_loop/select.c b/src/serialosc-device/event_loop/select.c
--- a/src/serialosc-device/event_loop/select.c
+++ b/src/serialosc-device/event_loop/select.c
@@
-		if (FD_ISSET(monome_fd, &rfds))
-			monome_event_handle_next(state->monome);
+		if (FD_ISSET(monome_fd, &rfds)
+				&& monome_event_handle_next(state->monome) < 0)
+			break;
#+end_src

This is the direct defense against the captured loop.  It also makes the
fallback use the error signal libmonome already supplies instead of assuming
that =select()='s exceptional set represents device disconnects.

It would be reasonable to make =poll.c= check the handler return too, for the
small race where the device disappears after the outer =poll()= but before the
read.  That is separate from, and much narrower than, treating errors on all
three descriptors as one condition.

*** libmonome #89

[[https://github.com/monome/libmonome/pull/89][libmonome #89]] adds =POLLHUP= and =POLLNVAL= to an existing =POLLERR=
check.  That is plausible defensive hardening, but it did not cause or fix the
captured failure: the capture included =POLLERR=, which upstream libmonome
already handles.  Its PR description should therefore retract the claim that
it fixed this particular CPU loop.  Unless someone can demonstrate a
=POLLHUP=-only or =POLLNVAL= case, closing it is also reasonable.

** Local Nix implications

The serialosc derivation now applies =disconnect-cpu-loop.patch= instead of
=poll-invalid-fds.patch=.  It has been built, installed, and tested as recorded
above.  The separate libmonome hardening patch remains applied, but it cannot
account for the change in behavior: it was already present in the broken
system, while the serialosc backend change was the new delta that made the
unplug test pass.

Future rebuilds that stage this =nix-jbb= tree with =bash/copy.sh= will retain
the repair.  Once upstream accepts an equivalent fix, the local patch can be
removed when the package is updated to a revision containing it.

** About the tracing mishap

The first tracing script launched =strace= in the background and then failed
to reap it.  That was my error.  It also caused the direct child to inherit
=/dev/null= as stdin, which serialosc interpreted as an IPC descriptor; those
=read(0)= calls in the trace are a test-harness artifact.  They do not alter the
device result: fd 3 independently became readable on unplug and generated the
captured =POLLIN | POLLERR | POLLHUP= cycle.

The trace script now keeps the traced process in the foreground, waits for an
explicit Enter key instead of an audio cue, and enforces a 15-second =timeout=
with a two-second kill grace.  The end-to-end verifier identifies only an
actual =serialosc-device= child of the current systemd supervisor, rather than
matching command-line text belonging to =strace=.  No further unplug
experiment is necessary to answer Artem's questions.
